# Rijo Code CLI

**by Rijoda Labs** — blazing-fast agentic coding harness in Rust, a native-speed
replacement for Python-based agent frameworks (Hermes Agent, Claude Code, Codex).

**Map of features and how they connect:** [`docs/ARCHITECTURE.md`](../ARCHITECTURE.md).

**Status:** early public release (v0.1.0), Linux-first, under active use as a
daily driver. Expectation: it works, but rough edges are documented
instead of hidden (see `CHANGELOG.md`, `SECURITY.md`).

## Installation (quick path)

```bash
git clone https://github.com/rijoda/rijo-code.git
cd rijo
./install.sh          # builds the release binary -> ~/.local/bin/rijo, no sudo
rijo                 # first start: short onboarding (provider, key, model)
```

**Windows (PowerShell):**

```powershell
git clone https://github.com/rijoda/rijo-code.git
cd rijo
powershell -NoProfile -ExecutionPolicy Bypass -File .\install.ps1
rijo                 # first start
```

No admin rights, no system directory. `-Prefix` picks another target,
`-SkipModels` skips the ~130 MB model download, `-SkipOnnx` omits the ONNX
Runtime, `-DryRun` only shows what would happen.

Prerequisites: Rust ≥ 1.75, git, an OpenAI-compatible API key. Linux tested on
Arch/Hyprland, Windows 11 measured (`docs/GOAL-100.md` §Z). Details, options
(`--prefix`, `--binary`, `--uninstall`), configuration and troubleshooting:
**[docs/INSTALL.md](../INSTALL.md)**.

**Desktop workbench (development):**

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\desktop-dev.ps1
```

Builds `target/debug/rijo-desktop.exe` and runs it against the Vite dev server
on `127.0.0.1:1420`, so HTML/CSS/JS changes apply live while the Rust core keeps
running. `-BuildOnly` only compiles, `-SkipBuild` reuses the existing binary.
Architecture, scope and the safety bridge: **[docs/features/desktop.md](../features/desktop.md)**.

## Providers

`rijo --list-providers` prints every ready-made provider with its endpoint, the
environment variable its key comes from and, where the provider has its own CLI,
the credential file it reads. Pick one for a single run:

```bash
# DeepSeek — the direct API (default model: deepseek-chat)
export DEEPSEEK_API_KEY=sk-...
rijo --provider deepseek
rijo --provider deepseek --model deepseek-reasoner

# OpenCode Zen/Go — includes the free development models
rijo --provider opencode --model space-bunny-free

# Anything else: point at the endpoint
rijo --base-url https://api.example.com/v1 --model some-model
```

Four rules that save a debugging round:

- **A foreign key is never reused.** Switching provider drops a key that belongs to
  another endpoint; reusing it earned a real HTTP 401 `AuthError: Invalid API key`.
- **A model you never chose is replaced, one you chose is not.** The built-in
  default is an OpenAI model and cannot work against another endpoint, so
  `--provider deepseek` without `--model` takes that provider's documented default,
  while an explicit `--model` is left alone.
- **Templates encode what each API insists on.** OpenCode needs
  `x-opencode-session` plus a browser-like User-Agent (without them: HTTP 400
  `MissingSessionID`, or Cloudflare 1010); DeepSeek needs neither.
- **These flags write nothing to `config.yaml`.** The key stays in the environment
  for that run.

Known context windows per model name (DeepSeek V4 = 1M, V3 = 128K, …):
`crates/rijo-core/src/models.rs`, overridable with `llm.context_window`.

### Web search

`web_search` uses the **built-in keyless DuckDuckGo Lite** engine — no external
service, no daemon, no API key. It speaks DuckDuckGo's Lite HTML endpoint
directly and unwraps the result redirects to the real URLs
(`crates/rijo-core/src/meta_search.rs`). The only search config is the request
timeout (`web.search_timeout_ms`) and the throttle cooldown
(`web.search_cooldown_secs`); a 24 h cache keyed by query + limit avoids repeats.

DuckDuckGo Lite is **scraped**, so it throttles after a burst. A failed call
sets a cooldown and `web_search` reports it clearly instead of hammering; the
default cooldown is short (60 s) so it recovers within a session.

There is no fallback provider by design: a dedicated search engine in Rust is
planned separately. `web_extract` (below) turns any URL into clean Markdown and
is the intended companion when a search step is needed.

Measured on this machine (2026-10-11, `--web-eval`, real network): DuckDuckGo
Lite answered with real hits (first query) but rate-limited the immediate
follow-up — the honest limit of keyless scraping.

Tool latency state (release build with LTO, `rijo --bench`, measured 2026-09-15
on this machine **under load** — load ~4.5 to 6.9; on an idle machine
`terminal_echo` is ~2 ms instead of ~6 ms, the spread is 2–37 ms per run):

| Tool | Rijo Code (μs) | Hermes reference (μs) | Speedup |
|---|---|---|---|
| read_file | 228 | 42,903 | 188x |
| write_file_small | 354 | 366,943 | 1,037x |
| search_files | 15,944 | 173,035 | 11x |
| skills_list | 1,066 | 441,026 | 414x |
| terminal_echo | 6,122 | 5,927,577 | 968x |

For scale: the bare process start of `bash -c 'echo hi'` costs 5.3–8.4 ms on
the same machine (idle: 2.3 ms) — more than the whole
Rijo Code tool call. The Hermes numbers come from `data/measure_hermes.py`
(direct Python tool calls, without an LLM). Reproduce both with
`./rijo --bench`.

## Goal

Eliminate the tool-call bottleneck: every tool that Hermes executes through a
Python interpreter runs here through native Rust — no interpreter boot, no
per-call overhead beyond what the OS itself charges.

## Benchmark method

`./rijo --bench` measures the tools in-process (warmup 2, median of 7) and
compares against the Python reference from `data/hermes_times.json`
(`data/measure_hermes.py` measures the Hermes tool functions directly, without an LLM).
Absolute numbers depend on load — hence the spread above instead of
pseudo-precision. Numbers update automatically when
`data/hermes_times.json` is regenerated.

## Parallel batch (2026-09-14, measured via `rijo --bench`)

Multiple tool calls in ONE turn no longer run strictly one after another:
consecutive **read-only** calls (read_file, search_files, skills_list,
skill_view, session_search, web_search, web_extract) are executed in parallel
as a batch — bounded by `max_concurrent_tools` (default 16). Everything
mutating/interactive (write_file, patch, delete_file, terminal, execute_code,
browser_*, delegate, TUI dialogs) breaks the batch and stays strictly ordered,
so that `read a → write b → read b` keeps exactly its semantics. `browser_*`
stay deliberately serial: one shared tab, navigate/snapshot would race.

Measured (median/average values, the same code path as the executor via
`run_parallel_batch`):

| Batch | sequential (before) | parallel (now) | Speedup |
|---|---|---|---|
| 8× local (search_files) | 179,0 ms | 46,8 ms | **3,83x** |
| 4× network (web_extract) | 1972,4 ms | 535,0 ms | **3,69x** |

The network measurement is opt-in (`RIJO_BENCH_NET=1 ./rijo --bench`) so that the
default bench runs deterministically and offline. Result order in the
transcript and in the UI remains the call order.

### Background processes (`process_manage`)

`terminal(background: true)` starts processes in a registry instead of letting them
drop: stdout/stderr go into **files** (`~/.rijo/data/proc/<id>.out|.err`)
— not into undrained pipes that block the process as soon as the buffer is
full — and the child handle is kept.

`process_manage` can then: `list` (all processes + status), `poll` (only the
output since the last poll), `log` (paged, line offset), `wait` (wait for the
end, with timeout), `kill`, `write`/`submit` (stdin, submit appends `\n`),
`close` (stdin EOF). Ids may be abbreviated as long as the prefix is unique.
On exit, `process::shutdown_all()` reaps all running processes.

Evidence: 2 unit tests (full lifecycle incl. exit code, incremental
poll, stderr, paged log, kill, stdin delivery, shutdown) and a real
run via `data/mock_process.json` — 9/9 OK, the output files contain the
real process output (`line-1..3`, `got:ping`), no orphans.

## Measured latency (2026-09-14, real runs)

Instrumentation: `src/metrics.rs` writes per run to
`~/.rijo/data/turn_metrics.jsonl` — startup phases and, for every turn,
`llm_ms` / `tool_ms` / `overhead_ms` / `total_ms` / iterations / tokens.
`rijo --bench` prints the aggregated evaluation (median, p95, max).
Tokens are **measured**, not estimated: `stream_options.include_usage`
returns the usage in the last SSE chunk.

Measured startup phases (one-off run):

```
brain_db_open           2 ms
registry_and_state    100 ms   (26 Tools)
websurfx_ready         15 ms
```

One-word answer via `--query`, turn 1: `total 1235 ms = llm 1235 ms +
tool 0 + overhead 0`, 4.402 prompt tokens, 1 iteration.

### Fixed: 100 s startup delay per run

Two causes, both measured and fixed:

1. The background indexing of the workspace held the embedder mutex for ~100 s
   (`blocking_lock`), and `run_turn` waited for it with `lock().await`. A
   one-word answer therefore needed **101.775 ms** of wall time (the turn itself:
   1.124 ms). Now: `try_lock()` — if the embedder is busy, the turn runs
   immediately with FTS5 full-text context instead of blocking.
2. One-off runs (`--query`, `--e2e`, `--bench`, `--tools`) no longer index
   the workspace at all — no turn follows that would benefit from it.

Result: **101.775 ms → 3.740 ms** wall time for the same run (27x).

### Fixed: prompt cache only hit the system prompt

`AHashMap` scatters the iteration order per process. The tool schemas were
sent in exactly this random order — so a different prefix on every start.
The provider's automatic prompt cache therefore only hit the part before it
(the system prompt) and reprocessed the ~2,900 tokens of
tool schemas every time. Conspicuous was that the hit stuck exactly at the
system prompt (1024 tokens), no matter how often the same request ran.

Measured with a local recording proxy (`--config` with a redirected
`base_url`, bodies compared byte by byte, three identical runs):

```
                          before            after
Cache hit (tokens)        1024 / 3967       3712 / 3967     26% → 94%
Cache miss (tokens)       2943              255             −91%
Request body             differs per run   byte-identical (sha256)
Tool order in the body    random            alphabetical
```

Fix: `Registry::get_names()` sorts (`crates/rijo-core/src/tools/mod.rs`).
That makes the prefix stable across process boundaries. Regression test
`tool_order_is_deterministic_and_sorted`: without the sorting it fails in 3 of
3 runs (two registries then return different orders).

Cross-check with the schema evaluation after the fix (`--variants full
--repeats 2`): tool choice 50/66, arguments 46/66 — no regression versus
49/66 and 45/66 from the reference run; the eval run itself reports 95 %
cache hit rate.

### Fixed: Websurfx never started from an existing checkout

`start_native` cloned into an already existing directory, `git clone`
failed, the start aborted silently and every search fell back to Wikipedia.
Now an existing checkout is only built (no second
clone), the build is deduplicated by a lock (parallel starts would otherwise
block each other on the cargo lock) and a failed build pauses for 10 minutes.

### Fixed: Websurfx search never returned results

Three bugs, each alone was enough for the silent Wikipedia fallback:

1. **Wrong parameter** — Rijo Code asked for `?format=json`; the search route of
   Websurfx expects `json=true` and returned the HTML page with `format=json`.
2. **Wrong field** — Websurfx returns `description`, Rijo Code read
   `content`/`snippet`, so hits arrived without a description.
3. **Missing cwd** — the binary was started without `current_dir` and died
   immediately with “Config file/folder not found!!” (config + public live in the
   checkout). The health check ran 9 s into nothing → `available: false`.
   Now the startup stderr is written to `~/.rijo/websurfx/.rijo-start.log`
   instead of being discarded — otherwise a startup failure is invisible.

Verified live: the instance starts (`websurfx_ready` 2015 ms, `available: true`),
search returns real hits (up to 21 results, including `hypr.land/news/update56/`).

Honest limitation: from this machine DuckDuckGo answers
unreliably (bot block). Then only the Wikipedia hits of the
meta-searcher come back — usable, but narrow. Other engines (Mojeek, Bing,
Brave, Qwant, Startpage, Yahoo) returned nothing at all in the test and are
disabled in the Websurfx config.

## Schema evaluation: measuring tool descriptions instead of guessing

The tool schemas are the largest part of the fixed prompt overhead per turn
(measured: 12.041 characters vs. 3.545 characters system prompt = 77 %). Shortening them
saves on EVERY turn — but a too-terse description costs the wrong
tool choice, and that costs a full roundtrip. That is why there is a
measurement setup for this instead of gut feeling:

    ./rijo --schema-eval                     # Basis, no_emoji, compact × 32 Aufgaben × 2
    ./rijo --schema-eval --limit 8 --repeats 1
    ./rijo --schema-eval --variants full,minimal,no_param_desc --repeats 3

Setup:

- **Task catalog** `data/schema_tasks.json`: 32 tasks that cover each of the 26
  tools at least once. Each one names the *acceptable* tools (several
  are intentional — often several paths lead to the goal) and substrings that must
  occur in the arguments. A test enforces the coverage: if a new
  tool is added and the catalog does not cover it, `cargo test` fails.
- **Shortening variants** (in `schema_eval.rs`): `full` (base), `no_emoji`
  (emoji prefix gone), `first_sentence` (first sentence), `no_param_desc`
  (parameter descriptions gone), `compact` (all together),
  `minimal` (only required parameters with type).
- **Measurement** with a real model, temperature 0 (otherwise variants are not
  comparable), non-streaming, with the real system prompt. `RIJO_LLM_MOCK`
  is deliberately rejected — scripted answers would falsify the measurement.
- **Output**: table (savings vs. tool hit rate vs. argument hit rate
  vs. latency vs. cache) plus the raw data as JSON under
  `~/.rijo/data/schema_eval/` — including the actual arguments of every
  wrong decision, so that it is traceable *why* a shortening was too terse.

Honest limitation: what is evaluated is the **first** tool decision. Legitimate
two-step cases (“first check whether the file exists, then write”)
count as a miss, although in the real loop the agent keeps writing after the tool
result. Such tasks fail equally in all variants — the
*comparison between variants* is unaffected by that, the absolute rate is
an approximation.

What `--schema-report` shows immediately (without an API call): the overhead is not
in the description texts, but in the **parameter schemas**. Example
`process_manage`: 174 characters description, 752 characters parameters. For
`skill_manage` it is 57 to 595. The five heaviest tools account for 37 % of the
entire schema overhead. Anyone who wants to shorten must therefore touch the
parameter definitions (types, enums, per-parameter descriptions) — not the prose.

The six shortening variants are built accordingly: `no_param_desc` (only the
parameter texts gone) and `minimal` (only required parameters with type) hit exactly
that spot, `first_sentence` and `no_emoji` the description.

**Result of the full run** (33 tasks × 2 repetitions = 66 runs
per variant, real model, temperature 0):

    Variant          chars    saving      tool pick  args       median   strict correct
    full               12041        0%      49/66      45/66    1380ms   45/66 (68 %)
    no_param_desc       8733       27%      50/66      46/66    1118ms   46/66 (70 %)
    compact             7768       35%      51/66      47/66    1196ms   47/66 (71 %)
    minimal             5529       54%      50/66      44/66    1160ms   44/66 (67 %)

Reading: the quality differences (1–3 runs out of 66) are within noise —
**no variant is measurably worse**, but all shortened ones are ~200 ms
faster in the median (13–19 %), and this effect is consistent across all three
shortened variants. Shortening is therefore safe; the only question is how far.

Two rules that the run demonstrates:

1. **Never remove parameters, only shorten their text.** `minimal` left out the
   `background` parameter for `terminal` — the model fell back to
   `nohup … &` on the command line. Type and enum remain complete.
2. **The parameter texts are the bulk**, not the prose
   (`process_manage`: 752 characters parameters vs. 174 characters description).

**Implemented (2026-09-14):** the shortening is now a permanent part of the
schemas — emoji prefix gone, tool and parameter texts terse, types/enums/
required fields unchanged. Measured before → after:

    Schema chars (sent)           12041 -> 10279   -14.6%
    Prompt tokens per turn         4402 ->  3977   -425 tokens (-9.7%)
    Tool pick (evaluation)       49/66 = 74% -> 77/99 = 78%
    Arguments (evaluation)       45/66 = 68% -> 71/99 = 72%
    Median latency (evaluation)   1380ms -> 1204ms  -13%

The accuracy differences are within noise (66 and 99 repetitions),
but nothing has become worse — with 425 fewer tokens per turn.

## Diagnostics feedback (2026-09-14, implemented — off by default)

After a change to a source file, Rijo Code can collect the compiler output
and **attach it directly to the tool result**. That saves the iteration
in which the model would otherwise call `cargo check` itself to find out whether
its edit even builds.

    diagnostics:
      after_edit: true          # default: false
      command: null             # null = autodetect (Cargo.toml → cargo check,
                                #        tsconfig.json → tsc, .py → py_compile)
                                # a custom command works too, {file} is substituted
      timeout_ms: 30000
      max_lines: 40

Measured for real on this project (a real model run that deliberately
introduced a syntax error and then removed it):

    patch with diagnostics, error case:     2057 ms   (cargo check bails out early)
    patch with diagnostics, success case:  22319 ms   (the check compiles through)
    without diagnostics (measured before):   ~200 ms

And the benefit in the same run: the model got

    crates/rijo-core/src/metrics.rs:250:14: error: this file contains an
    unclosed delimiter
    error: could not compile `rijo-core` (lib) due to 1 previous error

in the tool result and fixed the error in the following action — one
iteration saved (in the median ~1,2 s LLM roundtrip plus tool latency).

**Honest assessment:** on this Rust project the diagnostics cost 2–22 s per
change and save about one iteration per error found. That is a
bad deal when errors rarely arise — and a good one when a lot is
reworked and a missed error drags several iterations behind it.
That is why it is OFF by default and remains a deliberate decision.
Sensible use today: a custom, fast `command` (e.g. `cargo check -q -p
rijo-core` or a lint only for the changed file) instead of the full check.

## Context budget (2026-09-14, verified for real)

Without a budget the history grows without bound per turn — a single
terminal output can eat the rest of the session. Three levels, configurable
under `context:` in `~/.rijo/config.yaml`:

1. `tool_result_cap` (default 8000 characters): larger tool outputs are
   truncated; the **full text** lands in `~/.rijo/data/tool_out/<tool>_<id>.txt`
   and the path is passed to the model (reloadable via `read_file`/`search_files`).
   No loss of information, only no token eater.
2. `tool_stub_after_messages` (default 8): older tool outputs are trimmed to
   one-liners. The pairing `assistant.tool_calls` ↔ `tool` stays
   intact (otherwise 400 from the provider).
3. `max_messages` (default 80): hard upper bound. Only
   assistant/tool units are discarded — **every** user message (the task and later
   instructions) stays, so that the request is never left without a mandate.

Evidence: 5 unit tests for `prune_context` (trimming only outside the
grace period, idempotence, upper bound discards no user message, tool pairs
stay consistent, nothing happens below budget) and a real LLM run with
small thresholds — provider accepts the pruned history, no 400.
Fixture: `data/mock_context.json`, test config via `--config`.

## Approval gate for destructive actions (2026-09-15, after a real incident)

The starting point was a real run: `rm -rf ./*` was blocked three times — directly,
with an env prefix and with `export` — and the model deleted the workspace directly
afterwards via `execute_code` in a single step, because no gate was attached there. That
is the lesson: a gate that only checks the shell text of ONE tool is not a
protection, but a hurdle that a different spelling gets around.

Now, for all execution paths together:

1. A central module (`crates/rijo-core/src/guard.rs`) checks commands AND
   code payloads — used by `terminal` and `execute_code`.
2. Script path: `bash cleanup.sh` does not carry the pattern itself. The content of the
   file is read and checked too (max. 64 KB, also for an absolute path).
3. Self-approval is a failed attempt: if the command or the code contains
   `RIJO_APPROVE_DANGEROUS`, it is hard-rejected. Before, the error message
   even invited it ("set RIJO_APPROVE_DANGEROUS=1 and re-send") — three
   iterations were lost to that before the detour was taken.
4. Approval comes only from the user: TUI dialog as with `delete_file`, headless
   **rejected** by default. `RIJO_APPROVE_DANGEROUS=1` in the
   process environment remains the path for tests and pre-approval — it is never
   read from a payload.
5. The system prompt says it explicitly: do not circumvent, do not repeat in
   another tool, do not obfuscate with base64/eval — report and stand
   still.

Honest limit: this is a text heuristic, **not a sandbox**. Anyone who
switches the interpreter, drops a script via `write_file` and executes it,
base64-encodes the payload or assembles it only at runtime gets past. The
hurdle rises and the attempt becomes visible (tool trace + dialog), but real
guarantees only come with a sandbox (bubblewrap/Landlock) or a
restricted user. That is deliberately documented as an open point instead of
"resolved".

Proven: 7 unit tests in the guard module (the real incident as a test case, harmless
commands and payloads, one documented false positive, script content,
self-approval) plus two integration tests via the real registry:

- without approval: blocked `rm -rf`, blocked python path
  (`shutil.rmtree`), detected self-approval, checked script content —
  and harmless counter-samples that must run (otherwise the gate would be unusable);
- with approval: a programmatically played dialog (the same channel as in the TUI,
  y/Enter = yes, n/Esc = no) lets `rm -rf` and `delete_file` **really**
  delete; a rejection leaves the file untouched. The gate therefore does not forbid
  everything, but passes exactly the user's decision through.

The dialog code lives once in `guard.rs` (`dialog_blocking`/`dialog_async`) and
is used by `terminal` (destructive commands and sudo), `delete_file` and
`execute_code` — before, every tool had its own copy.

Audit trail: every decision lands as its own line in
`~/.rijo/data/guard_trace.jsonl` — `denied-headless`, `denied-by-user`,
`approved-by-user`, `approved-env` or `self-approval-rejected`, each with
target and reason (max. 400 characters). `tool_trace.jsonl` only says THAT a tool
failed; here the approval decision itself is recorded. Fixed along the way: the
tool trace had omitted the target path or the code for `delete_file`/`execute_code`
(`{}`) — so exactly for the destructive tools the traceable information was missing.
Long payloads are truncated to 400 characters.

## Long-running processes: the hanging server start (2026-09-15, fixed)

Symptom in the real run: the model wanted to check the built website live and
sent `cd … && python3 -m http.server 8712 >/dev/null 2>&1 & sleep 1; curl …`
as a **foreground** command. After that the turn stood still: no entry in
`tool_trace.jsonl` (the call never came back), the run ended there — and
bash + http.server stayed alive as orphans, port 8712 still occupied.

Cause: `exec_foreground` attached stdout/stderr to pipes. bash was done after
the `curl`, but the server kept the write end of the pipe open — the
subsequent `read_to_end()` waits for EOF, and that only comes when the
server ends. The timeout check only ran as long as the direct child lived; after
its end there was no deadline at all.

Four changes:

1. **Self-backgrounding is detected and redirected.** Commands with `&`,
   `nohup` or `setsid` (also without spaces, `&&`/`2>&1`/`&>file` do not
   count) go into the process registry: immediate answer with `session_id`,
   output into files, controllable via `process_manage`. The result marks
   that with `detected_backgrounding: true` and says how to check a server.
2. **`read_bounded` instead of `read_to_end`.** After the shell ends, reading
   continues non-blocking with a 300 ms budget. That is the safety net for
   every command whose child inherits the pipes — the shell is done, so the
   result is done.
3. **Process groups.** Foreground commands and background processes start in
   their own process group; timeout, `process_manage kill` and `shutdown_all`
   kill the whole group (`killpg`). Before, the server survived every
   abort as an orphan.
4. **System prompt.** For servers: `terminal` with `background: true`, then
   `process_manage`; check in a SEPARATE call
   (`curl -s -o /dev/null -w "%{http_code}" http://localhost:PORT/`); never
   send server output to `/dev/null`.

Proven with three integration tests via the real registry:

- the original command from the incident comes back in under 10 s, returns a
  `session_id` and can be terminated via `process_manage kill`;
- a foreground call whose grandchild inherits the pipes comes back in under 5 s
  (output still complete);
- a timeout kills the process group — the child process is really gone
  afterwards (check via `/proc/<pid>`).

Mutation cross-checked: with the redirect disabled the first test fails (and the
hanging call no longer blocks anyway thanks to `read_bounded` — both
levels work). 81 unit + 19 integration tests green.

Also fixed along the way: the repetition guard ended the turn **without an answer**
if the model repeated the same check three times (real: `browser_snapshot`
after a successful publish — the user only saw “query failed”, but the
work was done). Now the third identical call brings a hint
in the tool result (“do not repeat — take a different action or answer now”), and
only the next violation aborts. Logic as a pure function
(`repetition_decision`) with unit tests; 83 unit + 19 integration tests green.

## Learning review after the turn (2026-09-15, Hermes parity)

After every turn that had at least `learning.min_iterations` loops (default 2)
and a tool call, a separate LLM call (temperature 0,
`learning.max_tokens` = 800) evaluates the turn:

- Answer, tool calls (OK/FAIL, duration, args) and the existing skill names
  go in, a strict format comes out: `SKILL_CREATE:`, `SKILL_UPDATE:`,
  `MEMORY:` or `NOTHING`.
- Writing happens only to `~/.rijo/skills/<name>/SKILL.md` and
  `~/.rijo/data/memories/MEMORY.md`; skills in foreign libraries (Hermes)
  are never touched, names must match `[a-z0-9-_]`, at most 3 actions
  per review, no deletion.
- The run is a background task — the answer is not delayed. On
  exit (TUI exit and `--query`) the process waits a bounded time for an open
  review, so that the lesson is not lost.
- Costs are visible in `~/.rijo/data/turn_metrics.jsonl`:
  `"kind":"learn"` with prompt/completion tokens and duration. To switch off:
  `learning.after_turn: false` in `~/.rijo/config.yaml`.

`python3 scripts/ab_learning.py --dry` shows the configuration without starting

### Why the skill index must be in the system prompt (A/B measurement 2026-09-15)

## Terminal latency: 50 ms poll sleep removed (2026-09-15, measured)

`exec_foreground` polled the child process in a loop
(`try_wait` + `sleep(50ms)`). Because the first poll attempt practically always
returned “still running”, **every** command cost at least one sleep of
50 ms — regardless of how fast it was.

Rebuild: no more polling.

- One thread blocks on `child.wait()` and reports the end via a channel;
  the turn waits for the deadline with `recv_timeout`. Return at the moment
  the child ends.
- Two reader threads collect stdout/stderr permanently into buffers. That fixes
  a second bug at the same time: without reading along a child blocks as soon as the
  pipe buffer (~64 KB) is full — a chatty command then ran into the
  timeout instead of finishing.
- Wait briefly (300 ms) for EOF, then take what is there: if a grandchild holds the
  pipes open, the output is still complete.
- Timeout still kills the whole process group.

Measured with `rijo --bench` (median of 7, warmup 2):

```
terminal_echo   before  50.974 µs       after  2.549 µs     ~20x
Speedup vs. Hermes:  116x  →  2.325x
```

The remaining ~2,5 ms are almost entirely OS cost (starting `bash`,
running `echo`) — the lower bound for a process start on this
machine is ~1,8–2,3 ms. Safeguarded by two tests: `echo hi` must come back in under
30 ms, and 200 KB of output must not block the child.

## Architecture

```
┌────────────────────────────────────────────────┐
│  LLM Adapter (OpenAI-compatible HTTP API)      │
└───────────┬────────────────────────────────────┘
            │ tool calls (JSON)
┌───────────▼────────────────────────────────────┐
│  Tool Registry (AHashMap O(1) dispatch)        │
│  sync tools  → tokio spawn_blocking pool       │
│  async tools → native tokio runtime            │
└──┬─────────────────────────────────────────────┘
   │
   ▼
┌────────────────────────────────────────────────┐
│  Brain: Knowledge graph (petgraph) +           │
│  Vector store (cosine similarity, embeddings)  │
│  + cross-session context retrieval             │
│  + SkillLearner (auto skill create/improve)    │
└────────────────────────────────────────────────┘
```

### Learning review after each turn

`crates/rijo-core/src/learning.rs` — a cheap model call reviews the finished
turn (user request, tool calls with OK/FAIL, answer excerpt, existing skill
names) and answers in a strict format: `SKILL_CREATE`, `SKILL_UPDATE`, `MEMORY`
or `NOTHING`. It writes only into `~/.rijo/skills/` and
`~/.rijo/data/memories/MEMORY.md`, at most 3 blocks, never deletes, and never
touches skills in a foreign library (e.g. Hermes'). What it costs is in
`turn_metrics.jsonl` (`kind: "learn"`, prompt/completion tokens, duration).

What the model can see is the point: the skill list (name + description, own
skills first, max 40) sits in the system prompt, because an A/B measurement
showed a learned skill on disk was never loaded while it stayed invisible —
0 skill lookups in 4 of 4 runs before, 2 of 2 after.

### Brain (SQLite index + embeddings)

`crates/rijo-core/src/brain/` — the workspace is chunked per language family
(Rust at `fn`/`impl`/`struct`, 80-line cap; docs at headings), embedded with
fastembed `bge-small-en-v1.5` (384 dimensions, English) and stored in
`~/.rijo/data/brain.db` as nodes with `workspace`, `source`, `label`
(`file.rs:197 — pub fn xyz`) and the embedding blob.

- `brain_search` (tool) returns file pointers, scores and excerpts (500 chars
  per hit, max 20) — a step before `read_file`, which real runs repeated 7–8
  times on the same file.
- Hits are scoped to the current workspace (`all_workspaces: true` lifts that):
  before the scoping, 8 of 74 indexed sources belonged to other projects, so the
  model was pointed at files that did not exist here.
- Only hits above `memory.min_score` (default 0.30) are used — an irrelevant
  pointer costs tokens and misleads. When the embedder is busy (indexing holds
  it), the search runs full-text and says so in the result instead of silently
  getting worse.
- **Hybrid retrieval**: with a working embedder both paths run — the embedding
  finds paraphrases, FTS5 finds the exact identifier — and the two ranked lists
  are fused by reciprocal rank (RRF, k=60). A document both paths like rises;
  either path's contribution survives. Mode is reported as `hybrid`, `vector` or
  `fulltext`.
- **Incremental indexing**: a `indexed_files` table (mtime + size + chunk count)
  decides per file whether it has to be read at all. A warm start is a stat pass;
  a changed file has its old chunks removed before the new ones are written
  (no ghost hits from deleted functions), and files that disappeared lose their
  nodes. Previously every start re-embedded what it could not recognise as
  unchanged — measured at 65–70 s per start.
- `brain_search` hits bump `access_cnt`, which is used as a **tie-break** in the
  ranking (a pointer that helped before wins among equals) — not as a score
  boost, because one number without evidence should not move results.
- Measured indexing cost (this 80-file repo): **cold 870.9 s** (988 chunks, one
  time, machine under load), **warm 20 ms and 16 ms**. Before, every start ran
  the re-embedding pass — real runs measured 65,372 ms and 70,357 ms. So the
  warm start went from ~65 s to ~18 ms; the first index of a repository stays
  expensive.
- Per turn the system prompt carries the top hits as pointers; `rijo --index`
  fills the index explicitly (one-shot runs skip background indexing).
- Honest gaps: the `edges` table exists but nothing writes to it (no graph layer
  yet — the "graph" part of the brain is schema only), and `relevance` is stored
  but never updated.
- Cost and effect are logged per turn: `brain_ms`, `brain_hits`,
  `brain_top_score`, `brain_mode` (`hybrid` | `vector` | `fulltext` | `off`).
  `memory.enabled: false` switches the brain off for measurement.

## Embedding model: downloaded once, at install time

The ONNX model and its tokenizer are ~130 MB. fastembed's default cache is
`./.fastembed_cache` — relative to the *working directory* — so every project
folder Rijo Code was ever started in got its own copy (128 MB each, found in
`~/Projects/rijo`, `~/Projects/test`, `test2`, `test3`, `openram`, …). The cache
now lives in one place and is fetched by the installer:

```bash
rijo --download-models       # one-off; the installer runs it
RIJO_MODEL_CACHE=/some/dir   # optional override
```

```yaml
memory:
  embedding_model: all-MiniLM-L6-v2   # fetched on demand, into the same cache
```

- Location: `~/.rijo/models/fastembed` (created on demand). `RIJO_MODEL_CACHE`
  overrides it; an empty value counts as unset. Note that fastembed also honours
  `HF_HOME`, which takes precedence — documented because it silently wins.
- `install.sh` runs the download after installing the binary, so the first turn
  never waits for it. `--skip-models` skips the step, a failed download is not
  fatal (it is retried on first use), and `--dry-run` names it.
- The size report uses `symlink_metadata`: the HuggingFace layout links each file
  in `snapshots/…` to a blob, so following the links counted everything twice
  (128 MB reported as 255 MB).
- Tests: the cache directory is independent of the working directory, an override
  works, the init options carry model *and* cache dir (the old code ignored
  `model_id` entirely), symlinks count once, and one test actually embeds text
  from a different working directory and asserts that no local cache appears and
  that the second load downloads nothing.

## Context tool: see and recall the conversation (2026-09-18)

The task `context` (29th tool) makes the conversation context visible and brings
old parts back on demand — the first two steps of the compression plan
(`.hermes/plans/2026-09-18_105329-chat-history-kompression.md`).

```
action: status | recall | show
```

- `status` — fill against the detected model window, message breakdown of the
  session, watermark state, and how much a compression block would save:
  `Füllstand 11k / 1.0M ≈ 1 % (letzte Anfrage, provider-counted); Session
  sess_20260923 mit 2 Nachrichten (~20 Tokens), keine Compression-Blocks`.
  The prompt size comes from the provider (last `prompt_tokens` in
  turn_metrics.jsonl), the rest from the session store — nothing is estimated that
  could be counted.
- `recall <keywords>` — searches THIS session's older messages through the FTS5
  index that already exists over every message. Each word becomes a prefix term,
  AND-combined; punctuation is split off, because `MATCH 'ZIMT-4711*'` is FTS5
  syntax and used to fail with "no such column: 4711" — a real recall that
  returned nothing although the message was right there. Measured: 1 ms in a real
  run, against 2-4 s for an LLM call.
- `show` — the stored compression blocks with their watermarks.

Storage side (step 1 and 2 of the plan, both done):

- `sessions.db` gained a `summaries` table
  (`session_id, upto_message_id, summary, summary_tokens, created_at`). The
  watermark `upto_message_id` is what makes a compression cost O(new messages)
  instead of O(the whole history) — and it is durable across restarts.
- `SessionWriter` writes many messages over ONE connection; `record_message`
  opened the database per message, which is fine for the interactive loop but
  wasteful for a whole exchange or an imported block.

Decisions taken for the remaining steps (documented in the plan): compress
automatically at 80 % of the detected window with a minimum saving of 2000 tokens
and at least 5 turns in between (so the provider prompt cache survives), blocks of
at most 1200 tokens with the last 12 messages verbatim, compact data-row segment,
FTS5 first and embeddings later.

**Row 1 — activity** (`app.running` ? live state : state + hints):

- spinner, phase (`✎ writing…` / `⚙ terminal` / `thinking…`), elapsed, and for a
  running tool its duration.
- `1204 ch · ≈42 tok/s` while answering — an ESTIMATE marked with ≈ (~4 characters
  per token): the provider reports its token count only at the end of the stream.
- `bg 2` — background processes still running (amber); a forgotten server is
  otherwise only noticed when the port is busy. Shown idle and running.
- `Ctrl+C aborts` while running; `Ctrl+O=details` and `↑ 42% · End=follow` when the
  chat is scrolled.

**Row 2 — measurements** (always visible):

- `ctx 4.0k/128k 3%` — prompt tokens of the last request against the model's
  context window. The window is detected from the model name
  (`crates/rijo-core/src/models.rs`, e.g. `deepseek-flash` → 1M,
  `deepseek-chat` → 128K, `gpt-4o` → 128K, `claude` → 200K, `gemini-2` → 1M);
  `llm.context_window` overrides it, `0` (the default) means auto, and an unknown
  model stays unknown — then only the size is shown, no invented denominator.
  (An API cannot be asked: the OpenAI-compatible `/models` endpoint lists ids, not
  limits.) Colour: dim below 60 %, amber 60-84 %, red + bold
  from 85 %, where pruning/compaction starts to bite. While a turn runs it shows
  the live ESTIMATE of the request being sent (`ctx ≈12k/128k 9%`), so the row is
  never empty — not even in the first turn.
- `ttft 620ms` — time to the first *streamed* token: the latency a user actually
  feels. A slow first token reads as "it hangs" while tok/s still looks fine
  afterwards, so it is its own segment (amber above 5 s).
- `Turn 1.4s · LLM 1.1s · Tools 200ms` — harness vs model split of the last turn.
- `3× · 5 Tool · →33 tok` — iterations, tool calls, completion tokens. The prompt
  side is not repeated here; that is the context gauge.
- `30 tok/s` — real throughput: provider-reported completion tokens over measured
  LLM milliseconds (a turn average, not an instantaneous rate).
- `Cache 80%` — share of prompt tokens served from the provider prefix cache.
- `2 failed` / `brain 4` — tool failures of the last turn and brain hits that
  survived the score floor. Shown only when non-zero: a segment that is almost
  always `0` costs width on every row.
- `sess 3 turn(s) · 40k tok` — session totals; a single turn hides what a long
  session costs.
- Before the first turn the row says `· no measurements yet` instead of staying
  blank (an empty row looks like a rendering bug and the layout jumps).

On narrow terminals segments are dropped from the end of a row, and a shortened
value list drops WHOLE values (marked with `…`) instead of cutting a number in
half — a cut "Cache 2…" reads like 2 %. Tests:
`both_rows_stay_visible_during_a_turn`, `data_row_explains_itself_before_the_first_turn`,
`status_line_prioritises_on_a_narrow_terminal`, `status_line_never_cuts_a_value`.

Diagnostics from the turn path (context pruning) go to
`data_dir/diagnostics.log` and are drawn nowhere — never as `eprintln!` (which

## Web search: two latency traps found and fixed (2026-09-16)

The tool was not slow because of the network — it was slow because of two bugs.

1. **A configured Websurfx was never used.** `.env` values live in Rijo Code's *sealed*
   store (on purpose: the model must not be able to read service URLs or secrets),
   but `search_websurfx` only read the process environment. So in every normal run
   the URL looked "not set" and the answer silently came from Wikipedia, even with
   a healthy daemon on port 8080. Fixed by resolving the URL from the environment
   first and then from the sealed store.
2. **A provider that hangs cost its full timeout on every single search.** The
   trace showed 16.6-17.6 s per call (Websurfx stuck, Wikipedia answering after the
   15 s client timeout, then the result was cached). Now there is a bounded
   provider timeout plus a cooldown:

```yaml
web:
  websurfx_timeout_ms: 10000   # above the provider's own upstream budget
  websurfx_cooldown_secs: 900  # after a failure, skip it instead of paying again
  cache_ttl_secs: 0            # 0 = 24 h
  extract_parallel: 5          # web_extract fetches this many pages at once
  wikipedia_api: null          # override endpoint (mirrors, tests)
```

Also changed:

- **One pooled HTTP client** instead of a client per call with a rotating user
  agent. A fresh client throws away the connection pool, so every request paid
  DNS + TCP + TLS again: Wikipedia API 448-484 ms on a fresh connection vs 322 ms
  pooled (measured).
- **`web_extract` fetches its (up to 5) URLs in parallel**, input order preserved.
- **The search cache key includes the limit** — a `limit=5` answer used to be
  served for a `limit=20` request, so the model silently got fewer results.
- **The Websurfx health probe** no longer calls `/health` (Websurfx answers its
  static page with HTTP 200 for *any* path, so a stuck daemon looked healthy) and
  no longer starts a second instance when the port is already taken (the start log
  showed `AddrInUse` from exactly that). It probes the JSON search route with the
  correct `json=true` parameter and adopts a stuck port with a warning instead.
- Recommended in the Websurfx checkout: `request_timeout = 4` in `config.lua`
  (was 30) so a dead upstream engine is bounded at the source, below Rijo Code's cap.

Measured on this machine (2026-09-16):

```
search, daemon stuck, old code          16673-17607 ms  (trace, 5 calls)
search, daemon stuck, new code, 1st call    8750 ms  (bounded by config)
search, daemon stuck, new code, later         376-428 ms  (cooldown -> Wikipedia)
search, daemon healthy, new code             1138 ms  (provider: websurfx, real hits)
search, cache hit                            0 ms
web_extract, 3 URLs in parallel              1389 ms
web_extract, same 3 URLs sequential (curl)   1499 ms
websurfx direct, 5 queries                   1.3-2.1 s
```

## GitHub without a `gh` process per call (2026-09-16)

Rijo Code has a native `github` tool: repository work through the REST API with the
pooled HTTP client it already has, instead of spawning the official `gh` CLI for
every question.

```
action: repo_view | repo_list | repo_create | repo_delete | branch_list |
        commit_list | pr_list | pr_view | pr_create | pr_merge | issue_list |
        issue_create | issue_close | release_list | release_create | run_list |
        search_repos | api | auth
```

- `repo` defaults to the git remote of the current workspace, so `repo_view` in a
  checkout needs no arguments.
- Reads are cached for `github.cache_ttl_secs` (default 30): a repeated question
  inside a turn costs no request at all. Any write drops the cache — a stale list
  after creating a PR is exactly the lie the model would otherwise repeat.
- Read actions join a parallel batch, writes break it. That is an args-aware rule
  (`is_parallel_safe_call`): one tool with read *and* write actions cannot be
  classified by name alone. Verified in a real run: two `repo_view` calls
  executed 17 ms apart in one batch.
- Errors are translated: 401 (token invalid → `gh auth login`), 403 (scope or
  rate limit, with the remaining budget), 404 (private repo without access, or a
  typo), 422 (validation).
- The token comes from `GH_TOKEN`/`GITHUB_TOKEN`, `github.token_env`, or
  `gh auth token` — never from a tool argument and never from config.yaml, so a
  shared config file carries no credential and a transcript cannot leak one.
- Approval (TUI dialog, like `delete_file`) is required for the writes that
  cannot be undone or that publish: `repo_delete`, `pr_merge`, `release_create`,
  and `repo_create` for a PUBLIC repository. Opening a PR or filing an issue runs
  without a dialog — asking for everything trains blind approval.

Measured on this machine (2026-09-16, warm cache, network bound):

```
pure REST round trip to api.github.com        432-679 ms   (median 597)
gh --help (no network, process start only)     93-96  ms
gh auth token (keyring read)                  114-192 ms
gh repo view                                  631-906 ms   (median 809)
github tool, first call in a process         1784 ms   (token discovery + TLS)
github tool, later call in the same process   390-710 ms (round-trip floor)
github tool, repeated read inside the TTL      no request (unit-tested)
```

Honest reading: the process start and the keyring read disappear (~200 ms per
call) and the connection is pooled, but GitHub's own round trip dominates from
this machine and does not get faster. The tool caches the repeated question on
top of that; `gh` never does.

## Sync between machines

Rijo Code can carry its state to another machine: learned skills, the memory file and
the brain index. The core is transport-agnostic — it writes and reads a portable
directory (`~/.rijo/sync`), and a *private git repo* or *rsync over a tailnet*
moves that directory. Merge rules live in the core, once, so both transports
behave identically.

```bash
rijo --sync-export     # write the portable directory (brain, skills, memory)
rijo --sync-import     # merge a received directory into this machine
rijo --sync-status     # show config + state of the last export
```

Why the merge is simple where it can be, and explicit where it cannot:

- **Brain nodes are content-addressed** (`code:<workspace-tag>:<file>:<hash of the
  chunk>`), so the same chunk has the same id on both machines: merging is a set
  union, not a conflict. Only `label` (it carries line numbers, so it differs per
  checkout) and `access_cnt` move — label last-writer-wins, counter takes the max.
- **Embeddings travel with the nodes.** A cold index of this repo cost 870 s
  (measured), so the other machine gets the vectors instead of re-embedding
  everything. Import refuses when `embedding_model` or `embedding_dim` differ —
  foreign vectors are worse than none, because they quietly degrade every search.
- **Skills** are markdown files: identical → skip, one side changed → take it,
  both changed → keep BOTH as `<name>.conflict-<host>.md` instead of guessing.
- **`MEMORY.md`** is a set of `§`-separated entries: union with dedupe, then the
  same 2200-character cap the memory tool enforces (oldest entries fall off).
- **Workspaces must be on an allowlist** (`sync.workspaces`): the index holds
  source code. A machine that checks the same project out somewhere else maps the
  path (`sync.workspace_map`), and the node ids get rebased so the local indexer
  does not create duplicates.
- **Never exported, ever**: `config.yaml` (API key), `.env`, caches
  (`websurfx/`, `chrome-cdp/`, `staging/`, `tool_out/`, `audio/`), process logs.

Config block:

```yaml
sync:
  enabled: true
  transport: git                     # git (private repo) | rsync (planned)
  repo: rijoda/rijo-code-sync           # used by the git transport
  branch: main
  workspaces:                        # brain allowlist; empty = nothing is exported
    - ~/Projects/rijo
  workspace_map: {}                  # remote path -> local path, if they differ
  on_start: pull                     # pull+import at start
  on_exit: push                      # export+push at exit
  interval_min: 0                    # 0 = only at start/exit
  auto_init: false                   # create the private repo on first start
```

The git transport (`rijo --sync-init`, automatic pull/push around a session) is
the next step; today the portable core plus `--sync-export`/`--sync-import` are in
place and tested, including a real end-to-end run: export on one data dir, import
into a fresh one, then a `brain_search` that answered from the imported index.

### Offline mode (mock provider)

`RIJO_LLM_MOCK=<script.json>` replaces the HTTP call with a fixed
turn script (`turns[]` with `content`, `reasoning`, `tool_calls[{name,arguments}]`).
This runs the complete loop (dispatch → tool result → next turn)
without API credit. What is tested is the harness, **not** the model.

## Providers: using the OpenCode free models for development (2026-09-23)

`--provider <name>` switches the endpoint for one run. `opencode` (OpenCode
Zen/Go, which includes the free development models) is the first template:

```bash
rijo --list-providers                                  # templates, no API call
rijo --provider opencode --model space-bunny-free      # interactive
rijo --provider opencode --model space-bunny-free -q "Read calc.py and find the bug"
```

The template exists because this endpoint needs three things that a plain
OpenAI-compatible config does not have — each one verified against the live API
on 2026-09-23, each one a silent failure without it:

* **The base URL is not the obvious one.** `api.opencode.ai` and
  `models.opencode.ai` answer every request with Cloudflare error 1010
  (browser-signature block) — including the `/models` listing. The API lives at
  `https://opencode.ai/zen/go/v1`.
* **A session header is mandatory.** Without `x-opencode-session` every request
  fails with HTTP 400 `MissingSessionID` — *"cannot be routed efficiently"*.
  Rijo Code sends `rijo-<pid>`; one id per run keeps a conversation on one backend.
* **The User-Agent must look like a browser.** The Cloudflare edge blocks the
  default reqwest agent (again error 1010), so the template sends
  `User-Agent: opencode/1.0 (linux; x64)`.

Beyond that it is an ordinary OpenAI-compatible endpoint: streaming (SSE with a
usage event), tool calls with arguments, and `reasoning_content` all behave as
Rijo Code already expects — verified by probing each of the three.

### Where the token comes from

Rijo Code never copies the token into its own config. Lookup order:

1. `api_key` in `config.yaml` / `RIJO_API_KEY` — used only when it belongs to
   the *same* provider (i.e. the config already pointed at that base URL).
2. the provider's own environment variable (`OPENCODE_API_KEY`),
3. the provider's own credential file (`~/.local/share/opencode/auth.json`).

Step 3 means a machine that already has `opencode` logged in needs no second
copy of the key — the same pattern the GitHub tool uses with `gh auth token`.
`--list-providers` prints whether a token is available, never the token itself.

Reusing a *foreign* key is a real bug this guards against: with the DeepSeek key
from `config.yaml` still in place, the first live run against OpenCode returned
HTTP 401 `AuthError: Invalid API key`. The key is now used only when the config
already targeted that provider (`providers::apply`), and a regression test
(`a_key_for_another_provider_is_not_reused`) holds that.

### Permanent setup

For a fixed development profile, put the endpoint in a second config file and
pass it with `--config` — no flag needed per run:

```yaml
# ~/.rijo/opencode.yaml
llm:
  base_url: https://opencode.ai/zen/go/v1
  model: space-bunny-free
  session_header: x-opencode-session
  extra_headers:
    - "User-Agent: opencode/1.0 (linux; x64)"
  context_window: 0        # 0 = detect from the model name
```

```bash
rijo --config ~/.rijo/opencode.yaml
```

`--model`, `--base-url` and `--provider` override the loaded config for one run.
Note that `--base-url` pointing at an OpenCode host adds the required headers
automatically, so a bare URL cannot produce a `MissingSessionID` loop.

## MCP server: the native tools for other agents (2026-10-01, verified)

`rijo mcp serve` exposes the 31 native tools to any MCP client over **stdio** — Claude Code,
Codex, Cursor, VS Code, Hermes. The surface is deliberately two meta-tools:

| Tool | Purpose |
|---|---|
| `list_tools` | every registered tool: name, description, toolset and JSON argument schema |
| `call_tool` | execute one tool by name with its arguments |

**Why meta-tools instead of 29 server tools:** the registry stays the single source of truth. A
renamed or added tool shows up in `list_tools` immediately, so the MCP surface cannot drift from
the native one. Names stay sorted (`Registry::get_names`) — the same determinism the prompt cache
relies on.

**The Guard applies unchanged.** `call_tool` goes through `Registry::dispatch`, so a tool's own
safety checks run exactly as in the TUI. The server is headless, so the Guard **denies dangerous
actions by default**; only `RIJO_APPROVE_DANGEROUS=1` on the server process opens that door.

Verified with a real stdio handshake (`initialize` → `tools/list` → `tools/call`): 31 tools
listed, `read_file` returned a file, and `terminal {"command":"rm -rf build"}` came back as
`BLOCKED (recursive delete) … denied by default`, with a matching `denied-headless` entry in
`~/.rijo/data/guard_trace.jsonl`.

Client configuration (Claude Code / Codex / Cursor style):

```json
{ "mcpServers": { "rijo": { "command": "rijo", "args": ["mcp", "serve"] } } }
```

Details and the full tool list: [`docs/MCP.md`](../MCP.md).
